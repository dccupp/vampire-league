RosterComponent — Build Documentation

Project: Vampire Fantasy Football League — React Frontend

Component: src/Components/RosterComponent/RosterComponent.js

Purpose: Full rewrite of the legacy RosterTableComponent. Displays the logged-in user's fantasy roster in a styled table, with roster slot structure derived from their league's roster rules.

1. Context — Why Rewrite?

The original RosterTableComponent had several structural issues inherited from early development:

  • Fetched the league member by getting all members for a user then filtering the array in JavaScript — one extra unnecessary call
  • Used a chained useEffect pattern where each effect set state that triggered the next effect — causing extra render cycles
  • Used useEffect + setState for roster slot construction (pure derivation with no side effects) — which should be useMemo
  • Made API calls sequentially that could have been parallelised
The new component applies the same design principles established during the MatchupComponent refactor — single useEffect for all data fetching, Promise.all for parallel calls, and useMemo for derived data.

4. Data Fetching — fetchRosterData useEffect

Dependency Array

useEffect(() => { ... }, [currentUser?.id, currentLeague?.league_id]);

Runs once on mount. Only re-runs if the logged-in user or active league actually changes — which would mean a completely fresh set of data is needed anyway.

Why One useEffect?

Chaining multiple useEffect hooks where each one sets state that triggers the next creates unnecessary render cycles and makes the data flow hard to follow. A single effect that owns all fetching keeps the sequence explicit and predictable.

Fetch Sequence

Step 1  →  await league member                   (sequential — need is_vamp + member.id first)
Step 2  →  Promise.all([ roster rules, rostered players, fantasy week ])  (parallel — independent)
Step 3  →  await NFL schedule                    (sequential — needs year/week from step 2)
Step 4  →  map schedule onto players             (pure JS — no API call)

Step 1 — League Member

const memberResponse = await axiosInstance.get(
  `/league_members/getLeagueMemberByLeagueAndUserId/${currentLeague.league_id}/${currentUser.id}`
);
const member = memberResponse.data;
setLeagueMember(member);
Improvement over old component: The old component called getLeagueMembersByUserId which returned an array of all leagues the user belongs to, then filtered it in JavaScript to find the right one. The new component uses getLeagueMemberByLeagueAndUserId — a direct lookup that returns exactly one record.

Step 2 — Parallel Fetches with Promise.all

const rosterTypeId = member.is_vamp ? 2 : 1;
const [rulesResponse, rosterResponse, weekResponse] = await Promise.all([
  axiosInstance.get(`/roster_rules/getRosterRulesByLeagueId/${currentLeague.league_id}/${rosterTypeId}`),
  axiosInstance.get(`/rostered_players/getRosteredPlayersByLeagueMemberId/${member.id}`),
  getCurrentFantasyWeek(),
]);

Promise.all fires all three requests at the same time and waits for all three to finish before proceeding. Since none of these depend on each other's response, there's no reason to wait for one before starting the next.

The is_vamp field from Step 1 determines which roster type to use — type 1 for standard members, type 2 for the vampire member.

Step 3 — NFL Schedule

const { year, week } = weekResponse.data;
const scheduleResponse = await getGamesByWeekAndYear(year, week);
const games = scheduleResponse.data || [];

This must be sequential because the URL requires year and week, which only become available once the getCurrentFantasyWeek() call in Step 2 completes.

Step 4 — Map Schedule onto Players

const playersWithSchedule = players.map(player => {
  const game = games.find(g => g.team === player.team);
  return {
    ...player,
    schedule: game ? {
      date: game.date,
      day: game.day,
      est_time: game.est_time || 'TBD',
      location: game.location || 'Unknown',
    } : null,
  };
});

No API call — pure JavaScript. Uses Array.find to match each rostered player's NFL team to that team's game entry, then spreads the game details onto the player object as a schedule property.

Error Handling and finally

try {
  // ... all fetch steps
} catch (err) {
  setError(err.response?.data?.message || err.message || 'Failed to load roster data.');
} finally {
  setIsLoading(false);
}

The finally block guarantees isLoading is always set to false — whether the fetch succeeded, failed, or threw an unexpected error. Without finally, a crash inside the try block could leave the component stuck in the loading state.

5. Roster Slot Construction — useMemo

Why useMemo Instead of useEffect?

The old RosterTableComponent used a useEffect that watched rosterRules and rosteredPlayers, computed the slots, then called setRosterSlots(slots). This is a pattern where pure computation (no side effects, no API calls) is being done inside an effect — which causes an unnecessary extra render cycle.

useMemo computes the value during the render rather than after it, eliminating that extra cycle and keeping the derived value in sync with its dependencies automatically.

const rosterSlots = useMemo(() => {
  if (!rosterRules) return [];

  const positionCounts = [
    { position: 'QB',    count: rosterRules.quarterback_count             || 0 },
    { position: 'RB',    count: rosterRules.running_back_count            || 0 },
    { position: 'WR',    count: rosterRules.wide_receiver_count           || 0 },
    { position: 'TE',    count: rosterRules.tight_end_count               || 0 },
    { position: 'WRT',   count: rosterRules.wide_receiver_tight_end_count || 0 },
    { position: 'FLEX',  count: rosterRules.flex_count                    || 0 },
    { position: 'BENCH', count: rosterRules.bench_count                   || 0 },
    { position: 'IR',    count: rosterRules.ir_count                      || 0 },
  ];

  const slots = [];
  positionCounts.forEach(({ position, count }) => {
    for (let i = 0; i < count; i++) {
      slots.push({ position, sPosition: `${position}${i + 1}`, player: null });
    }
  });

  return slots;
}, [rosterRules]);

Output Structure

Each entry in rosterSlots is an object with three properties:

PropertyExample valuePurpose
position'RB'The position type — used for validation and display
sPosition'RB2'The specific slot identifier — used as the React key and for player assignment
playernullPlaceholder — will hold the player object once assignment logic is added

6. Conditional Rendering — isLoading and error

if (isLoading) return <div className="roster-container">Loading...</div>;
if (error)     return <div className="roster-container">{error}</div>;

return (
  <div className="roster-container">
    // ... main content
  </div>
);

React evaluates the function top to bottom on every render. The two early returns act as guards — if either condition is true, React renders that simple element and stops. The main return at the bottom is only reached when both conditions are false (loading is done, no error occurred).
